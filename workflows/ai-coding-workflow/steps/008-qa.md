# 008 - QA

**Skill:** `qa`

**Status:** On-demand core step.

**Role:** Produce a manual test plan to validate behavior in real conditions.

**When to use:** After substantial work, before an important release, for a critical flow, user-facing impact, or explicit need for manual validation.

**Possible inputs:** PRD, task specs, diff, commits, chat context, full initiative, or task group.

**Actions:**

- derive QA cases from acceptance criteria, risks, and likely regressions
- produce an ordered manual test checklist
- cover happy paths, edge cases, and priority regressions
- cover responsive behavior, empty states, errors, permissions, basic accessibility, and visual consistency for frontend work
- propose execution steps when useful
- distinguish test plan from real execution report

**Output:** session checklist, optional `qa.md`, or tracker equivalent.

**Artifact publication:** If a parent issue or sub-issue exists, propose publishing the QA plan or QA report as a comment: parent issue for initiative/release QA, sub-issue for slice-local QA. In local Markdown mode, propose `.initiatives/<initiative>/qa.md` only if the plan must be retained until closure.

**Output contents:**

QA plan:

- test scope
- prerequisites
- required data or accounts
- execution order
- happy paths
- edge cases
- responsive behavior and UI states when relevant
- permissions and errors when relevant
- regressions to watch

QA report, only if executed:

- observed results
- issues found
- manual verdict when applicable

Avoid:

- exhaustive permutations without priority
- invented or unobserved results
- replacing code review

**Possible sizes:** short checklist, or full QA plan for a release / critical flow.

**Human gate:** execute or supervise the real test and decide on issues.

**Important:** QA does not replace Review. The agent can produce the QA plan, but the human executes or supervises real validation, especially for sensitive flows and frontend work.
