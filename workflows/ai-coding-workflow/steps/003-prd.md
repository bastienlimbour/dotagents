# 003 - PRD

**Skill:** `prd`

**Status:** Required core step except for trivial changes.

**Role:** Product and functional source of truth. The PRD defines what is being built, why, for whom, and the expected observable behavior.

**When to use:** Before any non-trivial implementation. Detail level should match the scope.

**Possible inputs:** Clear idea, `brainstorming.md`, `brief.md`, `validation.md`, `grill-me` or `grill-with-docs` summary, user feedback, product constraints, project context, existing documentation.

**Actions:**

- choose the useful PRD depth: minimal, standard, or full
- consolidate problem, goals, target users, and value
- summarize already clarified context instead of restarting a full interview
- use canonical vocabulary from `CONTEXT.md` when available
- ensure technical details stay out of the PRD
- route back to `Grill Me` or `Grill With Docs` if important decisions remain unclear
- describe the product solution and expected behaviors
- define scope, non-goals, and success criteria
- detail flows, rules, states, errors, and edge cases when needed
- formalize acceptance criteria and functional verification
- provide an Execution Contract for a single-task initiative, or a base for `Slice` for multi-task initiatives

**Output:** canonical GitHub/tracker parent issue body by default, or local `prd.md` when local Markdown mode is selected.

**Artifact publication:** The PRD is the recommended point to create the parent GitHub issue or equivalent tracker item. Propose publishing the PRD in the canonical body of the parent issue; if a parent issue already exists, propose updating its body. Accepted alternative: create gitignored `.initiatives/<initiative>/prd.md` if the user selects local Markdown mode.

**Output contents:**

Required content:

- problem and goals
- target audience, personas, or affected users
- product-side solution
- `In Scope`
- `Out of Scope`
- essential behaviors, flows, or business rules
- important functional edge cases
- testable acceptance criteria
- functional verification
- blocking open questions

Conditional content:

- value proposition
- expected UI or system states
- expected error messages when relevant
- `Future Candidates`
- assumptions
- success criteria
- functional test decisions
- functional definition of done for a large initiative
- `Always do / Ask first / Never do` boundaries when useful

Avoid:

- stack choices, architecture, data model, endpoints, files, or migrations
- detailed implementation plan
- detailed technical test strategy
- full repetition of the brief or validation

**Possible sizes:** minimal PRD, standard PRD, or full MVP PRD.

**Human gate:** validate scope, ambiguous behaviors, acceptance criteria, and important product decisions.

**Important:** The PRD is a destination document, not eternal truth. It does not contain stack choices, architecture, data model, endpoints, libraries, file names, migrations, or implementation details.

If implementation or test decisions emerge during PRD work, include them only if they are already validated and useful for product understanding. Otherwise, move them to `Tech Design` or `Slice`.
