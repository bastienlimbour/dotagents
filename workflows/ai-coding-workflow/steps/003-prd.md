# 003 - PRD

**Skill :** `prd`

**Statut :** Core requis sauf changement trivial.

**Rôle :** Source de vérité produit et fonctionnelle. Le PRD fixe ce qu'on construit, pourquoi, pour qui, et le comportement observable attendu.

**Quand l'utiliser :** Avant toute implémentation non triviale. Niveau de détail proportionné au scope.

**Inputs possibles :** Idée claire, `brainstorming.md`, `brief.md`, `validation.md`, synthèse `grill-me` ou `grill-with-docs`, retours utilisateurs, contraintes produit, contexte projet, doc existante.

**Actions :**

- choisit le niveau de PRD utile : minimal, standard ou complet
- consolide problème, objectifs, cible et valeur
- synthétise un contexte déjà clarifié au lieu de relancer une interview complète
- utilise le vocabulaire canonique de `CONTEXT.md` si disponible
- vérifie que les détails techniques restent hors PRD
- renvoie vers `Grill Me` ou `Grill With Docs` si des décisions importantes restent floues
- décrit solution produit et comportements attendus
- fixe scope, non-goals et success criteria
- détaille flows, règles, états, erreurs et edge cases si nécessaire
- formalise acceptance criteria et vérification fonctionnelle
- fournit un Execution Contract si single-task, ou une base pour `Slice` si multi-tâches

**Output :** body canonique d'issue parente GitHub/tracker par défaut, ou `prd.md` local si le mode Markdown local est choisi.

**Publication de l'artefact :** Le PRD est le moment recommandé pour créer l'issue parente GitHub ou tracker équivalent. Proposer de publier le PRD dans le body canonique de l'issue parente ; si une issue parente existe déjà, proposer de mettre à jour son body. Alternative acceptée : créer `.initiatives/<initiative>/prd.md` gitignored si l'utilisateur choisit le mode Markdown local.

**Contenu de l'output :**

Contenu obligatoire :

- problème et objectifs
- cible, personas ou utilisateurs concernés
- solution côté produit
- scope `In Scope`
- `Out of Scope`
- comportements, flows ou règles métier essentiels
- edge cases fonctionnels importants
- acceptance criteria testables
- vérification fonctionnelle
- questions ouvertes bloquantes

Contenu conditionnel :

- proposition de valeur
- états UI ou états système attendus
- messages d'erreur attendus si pertinent
- `Future Candidates`
- assumptions
- success criteria
- décisions de test fonctionnel
- definition of done fonctionnelle si grosse initiative
- boundaries `Always do / Ask first / Never do` si utile

À éviter :

- choix de stack, architecture, data model, endpoints, fichiers ou migrations
- plan d'implémentation détaillé
- stratégie de test technique détaillée
- répétition complète du brief ou de la validation

**Tailles possibles :** PRD minimal, PRD standard, ou PRD complet MVP.

**Gate humain :** valider scope, comportements ambigus, acceptance criteria et décisions produit importantes.

**Important :** Le PRD est un document de destination, pas une vérité éternelle. Il ne contient pas choix de stack, architecture, data model, endpoints, librairies, noms de fichiers, migrations ou détails d'implémentation.

Si des décisions d'implémentation ou de test émergent pendant le PRD, les intégrer seulement si elles sont déjà validées et utiles à la compréhension produit. Sinon, les déplacer vers `Tech Design` ou `Slice`.
