# 008 - QA

**Skill name:** `qa`

**Step type:** Core, recommended (when manual validation is useful).

**Role:** Turn built behavior into an actionable manual validation plan and, when executed, a clear report of observed results.

**When to use:** After substantial work, before an important release, for a critical flow, user-facing impact, cross-browser concern, or explicit need for manual validation.

**Possible inputs:** Spec, task specs, diff, commits, QA context, review findings, built feature, target environment, browser/device requirements, required accounts, seed data, feedback commands.

**Process:**

1. Decide whether the step is producing a plan, executing checks, or summarizing observed results.
2. Determine setup, dev server, build, browser, or e2e commands from project docs, scripts, CI, current task context, or existing tests; report command drift when discovered guidance is missing, stale, or insufficient.
3. Identify critical flows, risk areas, required accounts, seed data, environment, devices, browsers, and viewport sizes.
4. Derive QA cases from Spec requirements, task acceptance criteria, risks, and likely regressions.
5. Order checks by user value and risk.
6. Cover happy paths, edge cases, permissions, errors, empty states, and priority regressions.
7. Include responsive behavior, basic accessibility, and visual consistency for frontend work.
8. When executing, collect real evidence such as console output, network behavior, DOM state, screenshots, accessibility checks, or e2e output.
9. Separate planned checks from observed results.
10. Classify each issue found by cause: implementation defect, unclear expected behavior, vocabulary/domain ambiguity, regression risk, or release risk.

**Rules:**

- QA validates behavior in real conditions. It complements code review rather than replacing it.
- Do not report planned checks as passed unless they were actually executed.
- Keep prerequisites explicit enough for another human to run the plan.
- Frontend QA should include desktop and mobile behavior when relevant.
- Failed or ambiguous QA should classify each issue by its cause so the right follow-up is obvious.

**Output:** Markdown QA plan, and QA report only when checks were actually executed.

**Output location:** Recommended default: ask before writing or updating local `.initiatives/001-<initiative>/qa.md`. Ask before publishing to a parent issue, task issue, PR, or tracker comment when coordination or auditability matters. If the user does not confirm, keep the QA plan or report in session only.

**Output template:**

```markdown
# <Initiative or Task> QA

## Scope
<!-- Required. Paragraph, 1-3 sentences: feature, task group, or release area covered. -->
<QA scope.>

## Prerequisites
<!-- Required when setup is needed. Bullet list. -->
- <Environment, account, seed data, flags, build, or setup.>

## Test Matrix
<!-- Conditional. Metadata list: include only relevant dimensions. -->
- **Browsers / devices / viewports:** <Targets when relevant.>
- **Roles / permissions:** <Targets when relevant.>

## Checklist
<!-- Required. Checklist grouped by user value and risk. -->

### Happy Paths
- [ ] <Primary user flow.>

### Edge Cases & Errors
- [ ] <Important edge case or error state.>

### Regressions
- [ ] <Adjacent behavior to recheck.>

### Frontend Checks
- [ ] <Responsive, accessibility, visual, loading, or empty state check.>

## Observed Results
<!-- Conditional. Bullet list: only checks actually executed, with evidence when useful. -->
- <Observed result and evidence.>

## Issues Found
<!-- Conditional. Bullet list: issue, severity, reproduction, classified cause, and link if created. -->
- **<Severity>:** <Issue found, reproduction, link if created, and cause: implementation defect / unclear expected behavior / vocabulary or domain ambiguity / regression risk / release risk.>

## Verdict
<!-- Required. Single line. -->
Pass / Pass with risks / Fail / Not executed
```

**Possible sizes:** lite (smoke checklist for a small change); standard (user-facing feature); full (critical flow, release, or audit-sensitive change).

**Verification:** The QA plan is executable by a human, and any report clearly separates observed results from planned checks.

**Human gate:** Execute or supervise real validation and decide what to do with issues found.
